# DECISIONS.md — networth-tracker

Зачем этот файл: код показывает, что сделано. Он не показывает, какие варианты
были отвергнуты и почему. Ниже — развилки из чата с Claude Code, которые иначе
умерли бы вместе с архивом сессии.

---

## Хранение данных: Supabase, а не localStorage

**Отвергнуто:** чистый localStorage (был явно прописан в исходном CLAUDE.md
в разделе "Важные ограничения" — "никакого бэкенда, никакой авторизации").

**Выбрано:** Supabase (Postgres + Auth) с RLS по `user_id = auth.uid()`.

**Почему:** нужен доступ с нескольких устройств (телефон + комп), а
localStorage привязан к одному браузеру. Сам CLAUDE.md на момент старта
противоречил себе — в разделе "Стек" уже была фраза про "минимальную
авторизацию как в проекте с привычками", но в "Ограничениях" это
перечёркивалось. Решили в пользу Supabase, документ поправлен по ходу.

**Публичность репозитория и sitецена этого решения:** GitHub Pages — статика
без сервера, значит сам фронтенд физически открыт всем по URL. Это ок именно
потому что данные защищены не секретностью кода, а RLS + логином: без сессии
Postgres отдаёт `permission denied` на уровне грантов, а не просто пустой
список (см. ниже).

## Способ входа: email+пароль

В соседнем проекте с привычками — тоже email+пароль (ранняя запись, будто там
magic link, ошибочна и исправлена 2026-08-15). Здесь выбор тот же и осознанный:
при прямом выборе между двумя вариантами предпочли "email + пароль". Если
понадобится сменить — это чисто фронтовая правка в `src/pages/Login.tsx` +
`src/contexts/AuthContext.tsx`, схема БД не завязана на способ входа.

## Отдельный Supabase-проект, а не общий с другими приложениями

**Отвергнуто:** переиспользовать Supabase-проект от привычек.

**Почему:** один аккаунт Supabase = много независимых проектов, как
организация на GitHub с несколькими репозиториями. Данные networth не должны
физически лежать в той же базе, что и привычки — разные жизненные циклы,
разные RLS-политики, никакой причины шарить.

## TypeScript, а не JS

Явный выбор при старте: структура снимка (Snapshot) вложенная и с полями вроде
`amount`/`priceUSD`, где опечатка в поле — тихий баг в подсчёте networth, а не
ошибка на этапе разработки. Типы окупаются уже на данных такой формы.

## Snapshot.assets — один jsonb-блоб, а не нормализованные таблицы

**Отвергнуто (неявно, не обсуждалось отдельно, но стоит зафиксировать):**
раскладывать banks/crypto/inventory/physical по отдельным SQL-таблицам с
foreign key на snapshot_id.

**Выбрано:** `snapshots.assets jsonb`, структура — прямое отражение
концептуальной модели из CLAUDE.md.

**Почему:** это личный инструмент одного пользователя, не аналитическая
система с произвольными джойнами. Категории активов и так гетерогенны
(у крипто-холдинга есть `tokens[]`, у банка — нет), нормализация добавила бы
3-4 таблицы и миграции ради запросов, которых никогда не будет. jsonb даёт
гибкость строго там, где она нужна (произвольные токены в кошельке), и не
мешает `total_usd`/`usd_rub`/`period` быть обычными индексируемыми колонками.

## RLS + явный GRANT только для `authenticated`, не для `anon`

**Найденная ловушка:** Supabase не даёт новым таблицам привилегий по
умолчанию. Первая проверка через анонимный REST-запрос вернула не пустой
массив (как ожидалось бы от одной только RLS), а `42501 permission denied for
table wallets` — то есть Postgres резал запрос ещё до применения RLS-политик.

**Решение:** `grant select, insert, update, delete on wallets, snapshots,
settings to authenticated;` — и **сознательно не** выдавать те же права
`anon`. RLS обычно и так отфильтровала бы для анонима все строки (`auth.uid()
= user_id` → false для null uid), но здесь двойная защита: даже гипотетическая
дыра в политике не даст анониму ничего прочитать, потому что у роли просто нет
доступа к таблице на уровне грантов.

---

## HashRouter, а не BrowserRouter + 404.html-трюк

**Отвергнуто:** BrowserRouter с классическим GitHub Pages SPA-хаком
(404.html редиректит на index.html через sessionStorage).

**Выбрано:** HashRouter (`/#/wallets` вместо `/wallets`).

**Почему:** GitHub Pages — статика без серверных рефрейзов. 404-трюк работает,
но добавляет edge-case (query-параметры иногда теряются при редиректе) и лишний
файл инфраструктуры. Для личного инструмента некрасивый `#` в URL — не цена,
за которую жалко платить.

## Автобаланс кошельков: только ETH/EVM, BTC, SOL — не всё подряд

**Отвергнуто:** одинаковый уровень автоматизации для всех активов.

**Выбрано:**
- EVM-адреса, 7 сетей: Ethereum, BNB Chain, Polygon, Arbitrum One, Optimism,
  Base, Avalanche — через Etherscan V2, один ключ на все сети (`chainid`
  параметр), список в `EVM_CHAINS` в `src/lib/api/etherscan.ts`
- BTC — нативный баланс через Blockchair (без ключа, лимит ~30 req/day)
- BTC Runes — через UniSat Open API (нужен свой бесплатный ключ)
- Solana — нативный SOL и SPL-токены через публичный RPC
  (`solana-rpc.publicnode.com`, не официальный `api.mainnet-beta.solana.com` —
  тот блокирует браузерные запросы по CORS). SPL добавлены 2026-08-18, см. ниже
- CEX-балансы (Binance/Bybit) и NFT — **сознательно оставлены ручными**,
  автоматизация через API бирж потребовала бы хранить API-ключи с торговыми
  правами, что несоразмерно риску для личного трекера

**Почему именно этот набор сетей:** пользователь явно попросил "топ-10
блокчейнов, на которых могут быть деньги" вместо изначального минимального
набора (только Ethereum), аргумент — Etherscan v2 даёт мультичейн почти
бесплатно через один и тот же ключ, грех не воспользоваться.

## Частичный успех показывается как частичный успех (правило всех сетей)

**Найденный баг при живом тестировании:** изначальная реализация делала
`await fetchBtcBalance()` и `await fetchRuneBalances()` последовательно в одном
try/catch. Blockchair (30 req/day) исчерпал лимит раньше, чем мы успели
протестировать Runes — и из-за одного `throw` терялись оба результата, хотя
UniSat отработал бы нормально.

**Исправление:** каждый источник в собственном try/catch, ошибка одного
рендерится как отдельная строка с текстом причины, не блокируя данные другого.
Общий принцип: **частичный успех должен показываться как частичный успех**, а
не схлопываться в общую ошибку.

**Расширено 2026-08-18** со страницы `/wallets` на все сети и обе страницы:
правило переехало в `src/lib/walletAssets.ts`, функция `fetchWalletAssets`
возвращает `{ assets, errors }`, где `errors` — частичные отказы. Ими же теперь
пользуется форма среза, раньше повторявшая ту же логику своей копией.

## EVM-сети опрашиваются последовательно, а не через `Promise.all`

**Найденный баг при живой проверке (2026-08-18):** эфирный кошелёк на
`/wallets` целиком падал с ошибкой API. Семь сетей запрашивались параллельно
через `Promise.all`, а бесплатный тариф Etherscan V2 разрешает 5 запросов в
секунду на ключ. Лимит срабатывал, V2 отвечал `status:"0"`, `message:"NOTOK"`,
а полезный текст клал в поле `result`, которое код не читал, — пользователь
видел голое «NOTOK», и один отказ ронял все семь сетей.

**Отвергнуто:** уменьшить набор сетей до трёх-четырёх (потеря смысла
мультичейна), кэшировать ответы (лимит не про частоту заходов, а про запросы в
секунду внутри одного захода).

**Выбрано:** последовательный обход `EVM_CHAINS` с паузой 250 мс, ретрай с
нарастающей задержкой на ответах со словом rate limit, разбор всех трёх форм
ошибки V2 (`status`+`result`, `error.message`, HTTP-код) и `errors[]` вместо
общего `throw`. Одинаковый отказ на всех сетях — например невалидный ключ —
схлопывается в одну строку вместо семи копий.

**Цена:** обновление эфирного кошелька занимает ~2 секунды вместо мгновенного.
Приемлемо: страница открывается раз в месяц.

**Условие пересмотра:** платный тариф Etherscan или переход на другой источник
снимут ограничение — тогда паузу можно убрать, оставив изоляцию ошибок.

## Solana: обе токен-программы, символы из локальной карты, цена по минту

**Найденный баг:** solana-кошелёк показывал только нативный SOL, SPL-токенов не
было вовсе — их просто не запрашивали.

**Решения внутри исправления:**

- **Опрашиваются обе программы** — старая SPL Token (`Tokenkeg…`) и Token-2022
  (`Tokenz…`). Новые монеты выпускаются во второй, и на одной программе часть
  баланса невидима. Если отвечает хотя бы одна — показываем что есть.
- **Символы берутся из локальной карты `MINT_SYMBOLS`**, неизвестные минты
  показываются как `EPjF…TDt1v`. *Отвергнуто:* запрашивать имя токена у
  CoinGecko по адресу контракта (`/coins/solana/contract/{address}`) — это один
  запрос на каждый токен, а бесплатный тариф лимитирован по минутам. Символ в
  форме среза всё равно правится руками.
- **Цена неизвестных токенов — по адресу минта**
  (`simple/token_price/solana`), а не по символу. Символ у таких токенов
  выдуманный нами, по нему цену не найти, а адрес — точный ключ.
- **Отбрасываются нулевые аккаунты и NFT** (`decimals = 0`), несколько
  аккаунтов одного минта суммируются в одну строку.

## ERC-20 на EVM-сетях остаются ручными

**Отвергнуто:** `action=addresstokenbalance` в Etherscan V2 — эндпоинт платный
(Pro). Обход через `action=tokentx`: вытащить контракты из истории переводов,
потом спросить баланс по каждому — это десятки запросов на кошелёк при лимите
5 в секунду, то есть минуты ожидания ради страницы, которую открывают раз в
месяц. Blockscout как бесплатная замена не проверялся и в этой сессии проверен
быть не мог — сеть из облачного контейнера к этим хостам закрыта.

**Выбрано:** на EVM подтягивается только нативная монета, токены вносятся
руками. Это единственное место, где Solana сейчас автоматизирована лучше
Ethereum, и это осознанно.

**Условие пересмотра:** если на EVM-адресах регулярно лежат стейблкоины,
стоит проверить Blockscout вживую — у него открытый API без ключа и инстансы
под большинство нужных сетей.

## UniSat: `spacedRune`, а не `symbol`, как отображаемое имя Руны

Первая реализация (до живой проверки с реальным ключом) была best-effort по
описанию полей — предполагали `runeSymbol`/`symbol` как тикер. Живой запрос
2026-07-09 показал: `symbol` — декоративный однобуквенный глиф (`¤`, `⧉`), не
имя. Переключились на `spacedRune` (например `BABYODIN•ID•NWKQ•ODIN`) как
единственное человекочитаемое поле в ответе.

## Предзаполнение формы снимка: разная стратегия для кошельков и остального

**Кошельки (self-custody из `/wallets`):** пересобираются заново каждый раз из
таблицы `wallets` (источник истины), а не копируются из прошлого снимка — так
удаление/добавление кошелька в `/wallets` сразу отражается в новой форме.
Токен-суммы внутри каждого кошелька при этом берутся из прошлого снимка как
стартовое значение (по совпадению `address`), пока не нажата "Обновить
балансы".

**Банки/инвентарь/физика/CEX:** не имеют отдельной таблицы-источника (в
отличие от кошельков), поэтому единственный способ не вбивать всё заново —
скопировать соответствующие строки из **последнего** снимка. Выбрано
пользователем явно при прямом вопросе "предзаполнять или пустая форма" —
аргумент: банки и товарные позиции не меняются от снимка к снимку, меняются
только суммы.

## Итог в USD: только RUB и USD, без мультивалютности

CLAUDE.md с самого начала ограничивал валюты банков/инвентаря/физики парой
RUB/USD с ручным курсом. При явном вопросе "нужны ли другие валюты (EUR и
т.п.)" пользователь не ответил — решение оставлено по умолчанию: **только
RUB и USD**, RUB конвертируется делением на введённый `usd_rub`. Если
понадобится EUR или другая валюта — это будет отдельное расширение
`categoryTotals()` в [src/lib/valuation.ts](src/lib/valuation.ts), не
архитектурная переделка.

## Снимки неизменяемы — в data layer нет функции update

Прямое следствие явного пункта UX в CLAUDE.md ("снимок = иммутабельная запись,
нельзя редактировать прошлое"). `src/lib/snapshots.ts` физически не
экспортирует `updateSnapshot` — не because "не успели", а потому что это
осознанно исключённая возможность. Уникальность `(user_id, period)` в БД
предотвращает случайную перезапись месяца, ошибка от constraint показывается
пользователю как понятный текст, а не как сырой Postgres-код.

## Деплой: две неочевидные ловушки GitHub Actions, которые стоили реального времени

1. **PAT без scope `workflow`** — Windows Git Credential Manager кэшировал
   старый Personal Access Token без разрешения `workflow`. GitHub отклоняет
   пуш файлов `.github/workflows/*` таким токеном с чёткой ошибкой, но фикс
   (добавить scope в существующий токен, не пересоздавать) не очевиден с
   первого раза.

2. **Secrets ≠ Secrets.** GitHub различает **repository-level secrets**
   (Settings → Secrets and variables → Actions) и **environment-level
   secrets** (Settings → Environments → `<env>` → Secrets). Первая попытка
   добавить `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` попала в
   environment-scoped секреты окружения `github-pages` — но job `build` в
   [.github/workflows/deploy.yml](.github/workflows/deploy.yml) не объявляет
   `environment: github-pages` (только job `deploy` его объявляет), поэтому
   секреты были физически невидимы шагу сборки. Собранный бандл при этом не
   падал явной ошибкой — просто тихо содержал `throw new Error('Missing
   VITE_SUPABASE_URL...')` вместо реального URL, что нашлось только через
   прямую проверку содержимого JS-бандла на проде (`grep` по
   supabase.co/project ref), а не через логи workflow (сборка формально
   "зелёная" в обоих случаях).

**Урок:** зелёный workflow run ничего не говорит о том, что итоговый бандл
рабочий, если ошибка — не exception при сборке, а тихий undefined на этапе
рантайма. Проверка "докачаться до реального бандла на проде и погрепать
конкретную строку" оказалась единственным надёжным способом подтвердить факт.

## Бренд: вендорная копия токенов и знаков, а не сабмодуль и не npm-пакет

**Отвергнуто:** git submodule на `quietfault/marketing`, приватный npm-пакет
с токенами, копирование только цветов руками в CSS трекера.

**Выбрано:** файлы бренда скопированы в репозиторий — `src/styles/tokens.css`
(копия `brand/tokens/tokens.css`) и `src/assets/brand/*.svg` (знаки из
`brand/logo/`). Оба места помечены как вендорные: правка едет в маркетинговый
репозиторий и приезжает сюда копированием.

**Почему:** маркетинговый репозиторий приватный, а этот публичный и собирается
GitHub Actions — сабмодуль потребовал бы деплою доступ к приватному репозиторию
ради двух десятков килобайт статики. Npm-пакет — та же проблема плюс релизный
цикл ради файла, который меняется раз в полгода. Копия честнее: она видна в
диффе, не ломает сборку и прямо подписана источником и версией (брендбук 1.0).

**Цена:** копия может разойтись с источником. Смягчено тем, что версия
записана в шапке файла, а сам брендбук требует фиксировать изменения в
`brand/CHANGELOG.md` — при обновлении бренда достаточно перекопировать.

## Тёмная тема — по умолчанию, светлая — переключателем

Брендбук называет тёмную тему основной, а светлую отдаёт печати, письмам и
документам. В `tokens.css` это уже зашито: тёмная объявлена на голом `:root`,
светлая — под `[data-theme="light"]`. Поэтому в трекере ничего изобретать не
пришлось: без атрибута страница тёмная, переключатель ставит атрибут и пишет
выбор в `localStorage` под ключом `qf-theme` — тем же, что у панели маркетинга.

Тема применяется инлайн-скриптом в `<head>` до первой отрисовки: иначе при
выбранной светлой теме на долю секунды мигает тёмный фон.

**Системная тема (`prefers-color-scheme`) намеренно не учитывается.** У панели
маркетинга наоборот — она стартует от системной. Разница осознанная: там
светлая тема основная и повторяет бланк, здесь основная тёмная по брендбуку, и
уважение к системной настройке означало бы, что у половины заходов инструмент
выглядит не так, как задуман.

## Пирог разбивки: одна тональность акцента, а не пять разных цветов

**Отвергнуто:** взять категориальную палитру из панели маркетинга
(`--series-1…5`, синяя шкала) — она задокументирована и CVD-безопасна.

**Почему нет:** брендбук прямо говорит, что палитра панели не пересекается с
основной палитрой бренда, и что акцент у quietfault один. Синие доли рядом с
оранжевым акцентом читались бы как второй бренд на одной странице.

**Выбрано:** четыре ступени светлоты оранжевого (`--series-1…4` в
`src/styles/app.css`), для светлой темы — свой набор, а не инверсия. Долей
всего четыре, каждая подписана в легенде с суммой, так что различать их по
одному тону достаточно. Если категорий когда-нибудь станет больше пяти, это
решение придётся пересматривать — тональной шкалы на такое не хватит.

## Название приложения: «Срез»

**Отвергнуто:** «Net Worth Tracker» (английское имя при полностью русском
интерфейсе), «Итого», «Состояние», «Опись».

**Почему «Срез»:** это уже рабочее слово проекта — в `CLAUDE.md` с самого
начала написано «раз в месяц пользователь делает срез по всем активам».
Название совпадает с единицей данных (snapshot) и коротко: рядом со знаком в
шапке длинное имя не живёт.

Имя компании во всех местах пишется `quietfault` — строчными, слитно; это
правило брендбука, а не стилистика.

---

## Знак: «Пересборка» и в шапке, и в фавиконе

**Развилка:** брендбук делит знаки — «Пересборка» (полосы) для
представительских мест, «Разлом» (кольцо) для иконок внутренних инструментов.
Трекер попадает в обе категории: личный инструмент за логином, но лежит в
публичном портфолио.

**Выбрано владельцем:** «Пересборка» везде — лого-блок в шапке и на экране
входа, фавикон из основного знака. «Разлом» остаётся в своей роли: буллет
списка предупреждений (каждое предупреждение — найденный разлом, ровно как
описано в брендбуке) и разделитель между кошельками в форме среза.

---

## Репозиторий публичный, не приватный

Выбрано пользователем явно ("чтобы можно было работать в нём без оплаты" —
приватные репозитории с GitHub Pages исторически требовали платный план).
Принятый риск: исходный код, включая Supabase anon key, виден всем. Это
осознанно приемлемо, потому что anon key безопасен по дизайну Supabase — он
не даёт доступа к данным без RLS-проверки авторизованной сессии.

## Кошельки сданы с проверкой на моках, живая проверка — на владельце

**Запись восстановлена задним числом 2026-08-20** командой `/cleanup`: решение
принято 18 августа, но осело только в `STATUS.md` и пропало бы вместе с его
чисткой.

**Решение:** правки автоподтяжки балансов доводятся до конца и мержатся,
проверенные 16 тестами на замоканном `fetch`, а живая проверка на настоящих
ключах явным пунктом висит на владельце и до неё результат не считается
подтверждённым.

**Почему:** прокси облачной сессии отдаёт 403 на CONNECT к `api.etherscan.io`,
`solana-rpc.publicnode.com` и `open-api.unisat.io` — ни один запрос к живому API
из сессии физически не уходит. Тесты покрывают разобранные формы ответов и
отказов, но не отвечают на вопрос, такие ли формы отдаёт настоящий API.

**Что отвергли:**

- *Объявить готовым по зелёным тестам.* Ровно та ошибка, что уже стоила этому
  проекту дня: зелёная сборка с `undefined` вместо URL Supabase (запись про
  ловушки GitHub Actions выше). Зелёный прогон на моках не отличим от зелёного
  прогона на верных моках.
- *Остановиться и ждать, пока владелец прогонит вживую.* Он возвращается к
  проекту через недели; ветка простояла бы всё это время, а остальная работа
  сессии всё равно не проверяется живыми API.
- *Ключи владельца в сессию, чтобы постучаться самим.* Прокси всё равно не
  пускает, а ключи в переписке — лишний экземпляр секрета без выигрыша.

**Пересматривается,** если хосты API попадут в список разрешённых для сессии
или проверка переедет в браузер, который открывает сама сессия, — тогда
«сдаём с моками» перестаёт быть единственным вариантом.
